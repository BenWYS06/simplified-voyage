# Booking refactor, first design

Date: 2026-10-11 · Status: **partly superseded** on 2026-10-21 by the [booking saga design](../booking-refactor/DESIGN.md). Steps 0–1 stayed; the idempotency and saga parts were redesigned. Progress of this design: [PROGRESS.md](../booking-refactor/PROGRESS.md) entries 2026-10-11 → 2026-10-13.

## Intent

The original booking flow works on the happy path only. Use it to learn, in real code, the core patterns of distributed systems: race conditions, row locks, deadlocks, idempotency, saga, transactional outbox. Learning / CV project: no real users, prefer the common industry approach.

## Problems found in the original code

| Pattern | Bug | Where |
|---|---|---|
| Race condition | Two users can book and pay for the same seat; `BOOKED` is set without checking the previous status | `BookingServiceImpl.createBooking`, `SeatInstanceServiceImpl.updateSeatInstanceStatus` |
| HTTP idempotency | The result page calls `verifyPayment` in `useEffect` under `StrictMode` (runs twice), and again on F5; each call publishes `payment.completed` | `BookingSuccess.jsx`, `PaymentServiceImpl.verifyPayment` |
| Create idempotency | A double click creates two bookings and two payments | `BookingReview`, `PaymentRepository` |
| Kafka idempotency | No consumer deduplicates: emails twice, confirm twice | `PaymentEventListener`, `BookingNotificationListener` |
| Outbox | DB commit, then a separate `kafkaTemplate.send`; Kafka down after the commit = event lost | `PaymentServiceImpl`, `PaymentEventListener` |
| Saga | No compensation, no expiry; cancel doesn't release seats | `cancelBooking` |

## Decisions (2026-10-11)

- **Saga: orchestration**, booking-service is the orchestrator ([ADR-004](../decisions.md)).
- **Payment: VNPay** sandbox replaces Razorpay; the IPN is the source of truth ([spec](2026-10-12-vnpay-payment-design.md), [ADR-003](../decisions.md)).
- **Flyway in all 9 services with a DB**, Hibernate only validates ([spec](2026-10-11-flyway-migrations-design.md), [ADR-002](../decisions.md)).
- **Refactor safety:** don't run the original app first; verify each change by impact scan + compile ([ADR-010](../decisions.md)).
- **Tests:** Testcontainers for the concurrency cases.

## What changed, and why

1. **2026-10-13: the `Idempotency-Key` table is the wrong tool here.** The key is generated by the page, so a refresh creates a new key and a second booking. A crashed request leaves its key `IN_PROGRESS` forever. Proposed instead: Redis `SET NX` on a hash of (user, flight, sorted seats), with the payment row as the source of truth for the link.
2. **2026-10-13: duplicate IPNs and Kafka events** are handled by checking state in the database inside the same transaction, not by Redis or a `processed_events` table ([ADR-007](../decisions.md)). This part stayed.
3. **2026-10-17 → 2026-10-21: full redesign.** Redis for create idempotency was dropped: it is not in the same transaction as the booking insert and can lose keys. The redesign moved booking-service to PostgreSQL and uses a **partial unique index** on (user, flight, seats hash) over live statuses as the gate ([ADR-006](../decisions.md)). It also added the `AWAITING_PAYMENT` status, the outbox for every event and a recovery / expiry job. See [DESIGN.md](../booking-refactor/DESIGN.md).

## Lessons

- A design that looks right per step can be wrong for the whole flow; the redesign started from the full list of failure cases instead.
- Idempotency keys must come from the request's meaning (who, which flight, which seats), not from a page visit.
