# Flyway migrations in every service

Date: 2026-10-11 · Status: **done** (refactor step 0, groups A + D). Decision record: [ADR-002](../decisions.md).

## Intent

The schema was created by Hibernate (`ddl-auto: update`). Nothing recorded which schema a service expects, changes could silently fail (Hibernate never drops or alters a column type), and the refactor needs real schema changes (new columns, unique indexes, an outbox table). Every schema change must become a reviewed, versioned file.

## Goals

- Every service with a database owns its schema through Flyway: user, airline-core, flight-ops, location, seat, pricing, ancillary, booking, payment.
- Hibernate only checks: `ddl-auto: validate`. A mismatch fails at startup, not at the first query.
- The starting schema equals today's schema exactly, so existing data and code keep working.
- A local MySQL for development that creates every database on first start.

## Non-goals

- No data seeding through Flyway.
- No change to tables or columns in this step (the baseline is a snapshot).
- Notification and subscription have no database and are untouched.

## Options

| Option | Why not / why |
|---|---|
| Keep `ddl-auto: update` | Silent drift, no history, can't express unique indexes or data migrations |
| Liquibase | Works, but XML / YAML changelogs add a layer; plain SQL is easier to review |
| **Flyway with plain SQL** | Chosen: one `V{n}__description.sql` per change, readable in a PR, Spring Boot support |

## How it is made

- `spring-boot-starter-flyway` + `flyway-mysql` (version from the Spring Boot 4.0.2 BOM, Flyway 11.14.1) in the 9 `pom.xml` files.
- `V1__init.sql` per service: generated by running each service once with `ddl-auto=create` on an empty database, then `mysqldump --no-data`. Wrapped in `SET FOREIGN_KEY_CHECKS = 0/1` because the dump orders tables alphabetically.
- `ddl-auto` → `validate` in both places it is set: each `application.yaml` and `config-repo/application.yml`.
- `docker/docker-compose.dev.yml`: `mysql:8.0` on 3306, runs `docker/init-databases.sql` on first start.
- user-service's H2 test sets `spring.flyway.enabled=false`.
- Removed `docker/migrations/001-cleanup-seat-instances.sql` (the clean V1 replaces it).

## Verification

All 9 databases dropped, each service started with the real config: all started, `Successfully applied 1 migration`, no errors, `flyway_schema_history` = 1 row. `mvn test` user-service passed.

## Later changes

- 2026-10-22: booking-service moved to PostgreSQL; its `V1__init.sql` was rewritten in PostgreSQL syntax before any shared environment had run it ([DESIGN.md](../booking-refactor/DESIGN.md) step 1).
- Rule for everyone since: never edit a migration that has run; add `V{n+1}` (`.claude/rules/db-migrations.md`).
